# งานซ่อมยาวกับ SLA — `work_class`, โหมดนาฬิกา, และ KPI ที่แยกจาก SLA

วันที่: 2026-09-16
สถานะ: ออกแบบเสร็จ รออนุมัติก่อนทำแผน implement

---

## 1. โจทย์

เคส Network ไม่ได้เป็นงานชนิดเดียว

- **เชื่อมต่อ Wi-Fi · ไดร์เวอร์ Network · VPN · ปัญหาการเชื่อมต่อ** — จบได้ในหลักชั่วโมง ควรอยู่บนนาฬิกา SLA ตาม priority ต่อไปเหมือนเดิม
- **ซ่อม hardware · เดินสาย Network** — องค์กรกำหนด KPI ไว้ว่า **ช่างขององค์กรเอง 30 วัน · vendor 45 วัน**

วันนี้เป้าหมายปิดเคสเลือกจาก `request_type` → `priority` → `defaults()` เท่านั้น
(`app/Support/TicketSla.php` — `targetFor()`) ไม่มีมิติไหนที่บอกได้ว่า "งานชิ้นนี้ยาว"
งานเดินสายจึงวิ่งบนเป้าหมายของ priority แล้ว **หลุด SLA โดยที่ไม่มีอะไรผิดพลาด** —
อาการเดียวกับ RQ-2026-0048 ที่เป็นที่มาของ `sla_targets` ตอน 2026-09-13

`category` (hardware/software/**network**/other) มีอยู่ทุกเคสแล้ว แต่**ใช้แทนกันไม่ได้** —
Network ทั้งก้อนเป็น 30 วันจะทำให้เคส Wi-Fi มี slack 30 วัน จนตัวเลข SLA ไม่มีความหมาย

## 2. บริบทที่ต้องเคารพ

2026-09-13 ทีม **ถอน** `TicketStatus::Pending` และกลไกหยุดนาฬิกา SLA ออกทั้งหมด
เหตุผลที่บันทึกไว้: *การตัดสินใจเรื่องเป้าหมายต้องอยู่กับคนที่เป็นเจ้าของเป้าหมาย
ไม่ใช่คนที่บังเอิญถือเคสอยู่*

ดีไซน์นี้ให้ช่างเป็นคนเลือกลักษณะงาน ซึ่งขยับเดดไลน์ — ต้องอธิบายให้ได้ว่าต่างจากของที่ถอนไปยังไง

| | Pending (ถอนแล้ว) | `work_class` (ดีไซน์นี้) |
|---|---|---|
| คนถือเคสทำอะไรได้ | **หยุดนาฬิกาเอง** | **เลือกป้ายจากลิสต์ตายตัว** |
| ส่วนลดเท่าไหร่ | ไม่มีเพดาน คนถือเคสคุมเอง | super admin เป็นเจ้าของตัวเลขทุกตัว อนุมัติไว้ล่วงหน้า |
| ร่องรอย | ไม่มีเหตุผลบังคับ | บังคับกรอกเหตุผล + timeline + AuditLog |
| ค่าเริ่มต้น | ต้องไปกดถึงจะหยุด | `standard` ไม่ match กฎไหนเลย — ไม่มีทางแอบทับเงียบ ๆ |

## 3. การตัดสินใจที่ตกลงกันแล้ว

| คำถาม | คำตอบ |
|---|---|
| ใครตัดสินว่าเป็นงานซ่อมยาว | **ช่าง ตอนกดรับหรือระหว่างทาง** (คนที่เห็นงานแล้ว) |
| 30/45 วัน = วันทำการหรือวันปฏิทิน | **ตั้งได้เองภายหลัง** — เป็นค่าต่อแถวกฎ ไม่ฝังในโค้ด |
| ตัวเลข SLA บนหน้าจอ | **แยกเป็นสองตัว** — "SLA งานปกติ" และ "KPI งานซ่อม" (ทางเลือก ข) |
| ลำดับ scope | `work_class` → `request_type` → `priority` → `defaults()` |

## 4. โครงข้อมูล

### 4.1 `TicketWorkClass` — มิติใหม่บนเคส

`app/Enums/Ticket/TicketWorkClass.php`

| ค่า | ความหมาย |
|---|---|
| `standard` | ค่าเริ่มต้นของทุกเคส — ไม่ match กฎไหน ใช้ priority/request_type เหมือนเดิมทุกประการ |
| `repair_internal` | งานซ่อม hardware / เดินสาย โดยช่างขององค์กร |
| `repair_vendor` | งานซ่อมที่ส่งออก vendor |

คอลัมน์ `tickets.work_class` — string, **NOT NULL, default `'standard'`**
(ไม่ใช้ nullable เพราะ "ไม่มีค่า" กับ "เป็นงานปกติ" คือเรื่องเดียวกัน
สองวิธีเขียนเรื่องเดียวกันคือจุดที่มันเริ่มไม่ตรงกัน)

**ตั้งใจไม่ผูกกับ `category`** — เคส Hardware ที่ส่งเครื่องเข้าศูนย์เป็นรูปเดียวกันเป๊ะ
ผูกกับ Network จะได้ของที่ใช้ได้ที่เดียว

### 4.2 `SlaScope::WorkClass` — scope ที่สาม

`app/Enums/Ticket/SlaScope.php` เพิ่ม `case WorkClass = 'work_class';`

`precedence()` ใหม่:

```
work_class → request_type → priority → defaults()
```

**ทำไม `work_class` ชนะ `request_type`:**
`request_type` ถูกเลือกโดยคนกรอกฟอร์ม *ก่อนมีใครไปดูของจริง*
`work_class` ถูกเลือกโดยคนที่ *เห็นงานแล้ว* — ข้อมูลที่ใหม่กว่าและแม่นกว่าควรชนะ

**ทำไมมันปลอดภัย:** `standard` ไม่ match กฎไหนเลย → `work_class` ชนะได้เฉพาะตอนที่มีคน
ตั้งใจจัดประเภทจริง ๆ ต่างจากกรณี `priority` ที่**ถูกตั้งเสมอ**ตอนกดรับ
ซึ่งเป็นเหตุผลที่ `request_type` ต้องชนะ `priority` (ไม่งั้นกฎ request_type จะไม่มีวันทำงาน)

### 4.3 `sla_targets.clock` — โหมดนาฬิกาต่อแถว

คอลัมน์ `clock` — string, NOT NULL, default `'business'`

| ค่า | นับยังไง |
|---|---|
| `business` | เวลาทำการ (`TicketSla::hours()` — จ–ศ 08:00–17:00 หักพักเที่ยง) — พฤติกรรมเดิมทุกวันนี้ |
| `calendar` | เวลาจริง 24/7 นับตรง ๆ |

ตอบคำถาม "30 วันคืออะไร" โดยให้ admin ตอบเอง:

- `repair_internal` = 240 ชม. + `business` → 30 วันทำการ
- `repair_internal` = 720 ชม. + `calendar` → 30 วันปฏิทิน

**`clock` อยู่บนทุกแถวรวม priority ด้วย** ไม่ใช่เฉพาะแถว `work_class` —
ให้แถวสองชนิดมีความหมายต่างกันคือจุดที่อีกหกเดือนจะมีคนอ่านผิด
default `business` ทำให้ทุกแถวที่มีอยู่แล้วทำงานเหมือนเดิมเป๊ะ

`enum TicketSlaClock: string { case Business = 'business'; case Calendar = 'calendar'; }`
วางที่ `app/Enums/Ticket/` ข้าง `SlaScope`

## 5. การคำนวณ

### 5.1 `TicketSla::targetFor()` คืน `clock` มาด้วย

signature เดิม:
```php
/** @return array{hours: int, scope: ?SlaScope, value: ?string} */
```
ใหม่:
```php
/** @return array{hours: int, scope: ?SlaScope, value: ?string, clock: TicketSlaClock} */
```
กรณี fallback (`defaults()`) คืน `clock: Business` — เท่ากับพฤติกรรมเดิม

`rules()` ต้องเก็บ `clock` มาด้วย โครงเปลี่ยนจาก
`[scope][match_value] => hours` เป็น `[scope][match_value] => ['hours' => int, 'clock' => string]`

### 5.2 นาฬิกาสองโหมด

เพิ่มคู่ของ `addBusinessMinutes()` / `businessMinutesBetween()`:

```php
public static function addMinutesOn(Carbon $from, int $minutes, TicketSlaClock $clock): Carbon
public static function minutesBetweenOn(Carbon $from, Carbon $to, TicketSlaClock $clock): int
```

โหมด `calendar` = `$from->copy()->addMinutes($m)` และ `$from->diffInMinutes($to)` ตรง ๆ
โหมด `business` = เรียกของเดิม (ไม่แตะ logic ที่ทำงานอยู่)

**`resolveDueAt()` และ `pct_elapsed` ต้องใช้โหมดเดียวกัน** — ถ้าคิดเดดไลน์แบบปฏิทิน
แต่คิด % แบบเวลาทำการ แถบความคืบหน้าจะโกหก (เต็ม 100% ตั้งแต่ยังไม่ถึงครึ่งทาง)

`forTicket()` ต้องแยกให้ชัด: **นาฬิกาตอบรับ (response) ใช้ `business` เสมอ** —
เป้าหมายตอบรับเป็นค่าเดียวทั้งระบบ (`ticket_sla_response`) ไม่ได้ผูกกับแถวกฎ
มีแต่นาฬิกาปิดเคสที่แตกตามโหมด

### 5.3 `take()` / `assign()` ห้ามทับเดดไลน์ของ `work_class`

guard เดิมมีอยู่แล้วสำหรับ `request_type` — เหตุผลเดียวกันเป๊ะ:
*"งานเดินสายใช้เวลา 30 วัน" ไม่ได้เลิกเป็นความจริงเพราะช่างที่กดรับติ๊กว่าด่วน*
ขยาย guard ให้ครอบ `work_class` ด้วย — เงื่อนไขที่ถูกคือ
"scope ที่ชนะไม่ใช่ `priority`" ไม่ใช่การไล่เช็คทีละ scope

เดดไลน์ยังคิดจาก `created_at` เหมือนเดิม — เคสที่จัดประเภทวันที่ 5 ได้ 30 วัน
**นับจากวันแจ้ง** ไม่ใช่ 35 วัน ซึ่งตรงกับที่ KPI วัด

## 6. Guard rails

ช่างเป็นคนตั้ง `work_class` และมันขยับเดดไลน์ จึงต้องมีร่องรอยครบ

1. **permission ใหม่ `tickets.set_work_class`**
   ต้องใส่ครบสามที่: `Permissions::catalog()` · `permission-labels.ts` LIVE set ·
   `ticket` permission tree
   *(`PermissionMatrixTest` จับ drift นี้ได้ — เป็นบั๊กแบบเดียวกับ `employees.delete`
   ที่เพิ่งแก้ 2026-09-16)*

2. **บังคับกรอกเหตุผล** เขียนลง timeline `ticket_updates` ที่มีอยู่แล้ว (รอดจากการถอน Pending มา)
   เปลี่ยนประเภทเงียบ ๆ ไม่ได้
   **ไม่เพิ่มคอลัมน์ `work_class_from`/`to` ลง `ticket_updates`** — ตอนถอน Pending
   ทีมตั้งใจยุบ `status_from`/`status_to` ออกและทำให้ประวัติ migration เรียบ
   ข้อความของบันทึกพูดแทนได้ และ AuditLog เก็บ from→to แบบ query ได้อยู่แล้ว

3. **ไดอะล็อกโชว์เดดไลน์เก่า → ใหม่ ก่อนกดยืนยัน**
   ช่างต้องเห็นกับตาว่ากำลังให้เวลาตัวเองเพิ่มจาก 8 ชม. เป็น 30 วัน

4. **AuditLog** — ใคร เมื่อไหร่ จาก→เป็น

5. **ตั้งกลับเป็น `standard` ได้** (กรอกเหตุผลเหมือนกัน)
   ไม่งั้นกดพลาดครั้งเดียวติดถาวร

6. **ตั้ง `work_class` ได้เฉพาะเคสที่มีคนรับแล้วและยังไม่ปิด** (`status = in_progress`)
   ตรงกับกฎของ `addUpdate()` ที่มีอยู่ (เคสที่ยังไม่มีคนรับ/ปิดแล้วเขียนบันทึกไม่ได้)

   **ไม่ใช่พารามิเตอร์ของ `take()`/`assign()`** — เป็น action แยกที่ทำได้ทันทีหลังกดรับ
   หรือระหว่างทาง คนกดรับยังไม่ได้เปิดเครื่องดูจึงยังไม่รู้ว่าเป็นงานยาว
   และการรวมสองเรื่องเข้าด้วยกันจะทำให้ guard "กดรับไม่ทับเดดไลน์" (ข้อ 5.3)
   ต้องตัดสินสองอย่างในคำสั่งเดียว

## 7. ตัวเลขบนหน้าจอ — แยก SLA ออกจาก KPI (ทางเลือก ข)

### 7.1 ปัญหา

พอมีเป้าหมาย 360 ชม. อยู่ในระบบ `sla_met_pct` จะเอาเคส 4 ชม. กับเคส 360 ชม.
มารวมเป็นเปอร์เซ็นต์เดียว — เคส critical ที่หลุดกับงานซ่อม vendor ที่หลุดนับน้ำหนักเท่ากัน
ทำให้ตัวเลขอ่านยากขึ้น ไม่ใช่ง่ายขึ้น

30/45 วันเป็น **KPI คนละตัว** กับ SLA อยู่แล้วในความเป็นจริงขององค์กร

### 7.2 ที่อยู่ของโค้ด

`GET /api/tickets/summary` — `app/Http/Controllers/Api/Ticket/TicketController.php`
(ราวบรรทัด 250–315) **ไม่ใช่** `DashboardSummaryService`
การ์ดอยู่บน**หน้า Ticket** (`resources/js/modules/ticket/pages/index.tsx:716–722`)

### 7.3 สิ่งที่เปลี่ยน

แบ่งเคสที่ปิดในหน้าต่างเวลาออกเป็นสองกลุ่มด้วย `work_class`:

| กลุ่ม | เคส | ตัวเลข |
|---|---|---|
| งานปกติ | `work_class === standard` | `sla_met_pct` (คีย์เดิม ความหมายแคบลง) |
| งานซ่อม | `repair_internal` / `repair_vendor` | `repair_kpi_met_pct` (คีย์ใหม่) |

คีย์ใหม่ใน payload:
- `repair_kpi_met_pct: int|null` — null เมื่อไม่มีเคสซ่อมปิดในหน้าต่างนั้น (รูปเดียวกับ `sla_met_pct`)
- `repair_kpi_delta_pts: int|null`
- `repair_backlog: int` — งานซ่อมที่ยังไม่ปิด (เพื่อให้รู้ว่า null แปลว่า "ไม่มีงาน" หรือ "ยังไม่มีอันไหนปิด")

`sla_breached_now` **ยังนับรวมทุกเคส** — เคสซ่อมที่เลย 30 วันก็คือเลยกำหนดจริง
ไม่ใช่เรื่องที่ควรซ่อน

**เคสตกกลุ่มไหน ตัดสินจากค่า `work_class` ปัจจุบัน** ไม่ใช่ค่าตอนแจ้งหรือตอนปิด —
เคสที่ถูกตั้งเป็น `repair_vendor` แล้วตั้งกลับเป็น `standard` นับเป็นงานปกติ
(ค่าในคอลัมน์คือคำตอบเดียวที่มี และ AuditLog เก็บประวัติไว้ให้แล้วถ้าต้องสาว)

### 7.4 หน้าจอ

การ์ด "KPI งานซ่อม" เพิ่มข้าง "ปิด Ticket ทัน SLA" บนหน้า Ticket
**ซ่อนการ์ดเมื่อยังไม่มีกฎ `work_class` สักข้อ** — องค์กรที่ไม่ได้ใช้ฟีเจอร์นี้
ไม่ควรเห็นการ์ดที่ขึ้น `—` ตลอดกาล

**ต้องแก้ป้ายของการ์ดเดิมด้วย** — `sla_met_pct` เลิกนับเคสซ่อมแล้ว ป้าย
`ticket_sla_met` ที่วันนี้อ่านว่า "ปิด Ticket ทัน SLA" จึงกลายเป็นคำที่กว้างเกินจริง
เปลี่ยนเป็นทำนอง "ปิดงานปกติทัน SLA" **เฉพาะตอนที่การ์ด KPI โชว์อยู่** —
ถ้ายังไม่มีกฎ `work_class` ตัวเลขก็ยังครอบทุกเคสจริง ๆ ป้ายเดิมถูกอยู่แล้ว

## 8. หน้าจออื่น

**Settings → Tickets & SLA**
- ลิสต์ที่สาม "เป้าหมายตามลักษณะงาน" clone จากลิสต์ request type ที่มีอยู่

  (`sla_target` มี `scope`/`value`/`hours` อยู่แล้ว)

## 9. Migration — ไม่ขยับอะไรเลย

- `tickets.work_class` default `'standard'` → **ทุกเคสที่มีอยู่เป็นงานปกติ**
- `sla_targets.clock` default `'business'` → **ทุกแถวกฎที่มีอยู่ทำงานเหมือนเดิม**
- ไม่มีกฎ `work_class` สักข้อตอนติดตั้ง → `targetFor()` ให้ผลเท่าเดิมทุกเคส

**เทสต์ parity คือเงื่อนไขผ่าน**: ก่อน/หลัง เดดไลน์ของทุกเคสในระบบต้องเท่าเดิม
ตราบใดที่ยังไม่มีใครสร้างกฎ `work_class` — เป็นคุณสมบัติเดียวกับที่ `sla_targets`
ตั้งไว้ตอน 2026-09-13 (ตารางว่างได้ ทุกเคสยังได้เป้าหมาย)

## 10. เทสต์

ไฟล์ใหม่ `tests/Feature/TicketWorkClassTest.php` + เสริม `SlaTargetTest`

**ลำดับและการเลือกเป้าหมาย**
- ไม่มีกฎ `work_class` → ทุกเคสได้ผลเท่าเดิม (parity)
- `work_class` ชนะ `request_type` เมื่อเคสเข้าทั้งคู่
- `standard` ไม่ match กฎไหน แม้มีแถว `standard` อยู่ในตาราง
- กฎที่ปิดสวิตช์ถูกข้าม
- กดรับไม่หดเดดไลน์ที่มาจากกฎ `work_class`

**นาฬิกาสองโหมด**
- `calendar` 720 ชม. จากศุกร์เย็น → ครบในอีก 30 วันปฏิทินพอดี
- `business` 240 ชม. ให้ผลเท่าของเดิมทุกประการ
- `pct_elapsed` ใช้โหมดเดียวกับเดดไลน์ (ตั้ง calendar แล้ว % ต้องไม่กระโดด)
- นาฬิกาตอบรับยังเป็น `business` แม้กฎปิดเคสเป็น `calendar`

**Guard rails**
- คนไม่มี `tickets.set_work_class` → 403
- ไม่กรอกเหตุผล → 422
- เคสที่ยังไม่มีคนรับ / ปิดแล้ว → ปฏิเสธ
- เปลี่ยนแล้วมีบันทึกใน timeline และ AuditLog จริง
- ตั้งกลับเป็น `standard` ได้ และเดดไลน์กลับไปตาม priority

**ตัวเลขสรุป**
- `sla_met_pct` ไม่นับเคสซ่อม
- `repair_kpi_met_pct` นับเฉพาะเคสซ่อม และเป็น null เมื่อไม่มี
- `sla_breached_now` ยังนับรวมทุกเคส

**Permission drift**
- `PermissionMatrixTest` / `EmployeePermissionHierarchyTest` ยังเขียว
  (คีย์ใหม่ต้องอยู่ครบทั้ง PHP และ TS)

**พิสูจน์ด้วยการถอด guard ออกแล้วดูให้แดง** ตามธรรมเนียมโปรเจกต์ —
อย่างน้อยเงื่อนไข "กดรับไม่ทับเดดไลน์ของกฎ work_class" และ "pct ใช้โหมดเดียวกับเดดไลน์"

## 11. สิ่งที่ *ไม่* ทำ (YAGNI)

- **ไม่** รื้อ Pending / หยุดนาฬิกากลับมา — ถอนไปแล้วด้วยเหตุผลที่ยังใช้ได้อยู่
- **ไม่** เพิ่ม scope ตาม `category` — แก้ปัญหาไม่ตรงจุด (ข้อ 1)
- **ไม่** ให้ลากลำดับ precedence ได้ — ลำดับตายตัวข้อเดียว เหมือนที่ตัดสินไว้ 2026-09-13
- **ไม่** เก็บ `work_class_from`/`to` ลง `ticket_updates` — AuditLog ตอบได้แล้ว (ข้อ 6.2)
- **ไม่** ทำ workflow อนุมัติการเปลี่ยน `work_class` — เหตุผล + AuditLog พอสำหรับรอบนี้
  ถ้าพบว่ามีการใช้ผิด ค่อยเพิ่มทีหลังโดยไม่ต้องรื้อของเดิม
- **ไม่** แตะ `DashboardSummaryService` — การ์ด SLA อยู่บนหน้า Ticket (ข้อ 7.2)

## 13. ความเสี่ยงที่รู้ตัว

- **ช่างจัดประเภทผิดเพื่อหนี SLA** — คุมด้วยเหตุผลบังคับ + AuditLog + การ์ด KPI ที่แยกออกมา
  ทำให้เห็นว่ามีงานซ่อมเยอะผิดปกติไหม ไม่ได้คุมด้วยการห้าม
- **`repair_kpi_met_pct` จะมีตัวอย่างน้อยมากในช่วงแรก** (งาน 30 วันกว่าจะปิดชิ้นแรก)
  การ์ดจึงต้องแสดง `repair_backlog` ควบคู่ ไม่ใช่เปอร์เซ็นต์ลอย ๆ
- **`rules()` เปลี่ยนโครง** จาก `=> int` เป็น `=> array` — เป็น breaking change ภายใน
  ต้องไล่ทุก call site (ปัจจุบันมี `targets()` และ `targetFor()`)
