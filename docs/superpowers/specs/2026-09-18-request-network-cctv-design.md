# คำขอ Network และ CCTV + ขั้นอนุมัติแบบระบุฝ่าย

วันที่ 2026-09-18 · สถานะ: รอรีวิว

## สิ่งที่ต้องการ

เพิ่มชนิดคำขอใหม่สองชนิด พร้อมสายอนุมัติของแต่ละชนิด

```
Network   Requestor → Asst. Manager หรือ Manager → Vice President
CCTV      Requestor → Supervisor หรือ Senior Supervisor
                    → QC Dept. (Asst. Manager หรือ Manager)
                    → SE Dept. (Supervisor หรือ Manager)
                    → Vice President
```

`SE Dept.` = ฝ่ายความปลอดภัย (Safety, DEP-0007) ตามที่ยืนยันแล้ว

## สองงานนี้ยากไม่เท่ากัน

**Network ลงตัวกับเครื่องยนต์ปัจจุบัน** — `RUNGS['manager']` และ `RUNGS['executive']` มีอยู่แล้ว
เป็นการเพิ่มข้อมูล ไม่ใช่เพิ่มความสามารถ

**CCTV ต้องการความสามารถที่ยังไม่มี** — ขั้น `chain` ทุกวันนี้เดินขึ้นไปตาม *สายบังคับบัญชาของผู้ขอ*
เท่านั้น (`WorkflowResolverService::findHolder()` ไล่ใน `$chain` ซึ่งคือสายผู้จัดการของผู้ขอ)
แต่ QC และ Safety คือคนใน *ฝ่ายอื่น* ที่ไม่ได้อยู่ในสายนั้นเลย

## โครงสร้างที่มีอยู่และข้อจำกัด

```
StepActorType         chain · owner · it_staff            ← ไม่มีแบบ "ฝ่าย"
workflow_steps        workflow_id, position, actor_type, label, kind
workflow_step_positions  step_id × position_id            ← ใช้ซ้ำได้เป็นรุ่นตำแหน่ง
request_approvals     approver_employee_id (nullable), approver_name, acted_by_user_id, ...
RequestService:702    actor.employee_id === row.approver_employee_id   ← ผู้อนุมัติได้คนเดียว
```

ข้อจำกัดที่แท้จริงคือบรรทัดสุดท้าย: **หนึ่งแถวอนุมัติ = หนึ่งคนที่ถูกระบุชื่อตั้งแต่ตอนยื่น**
กระดิ่ง อีเมล และตัวเตือนคำขอค้าง ล้วนอ่านจาก `approver_employee_id` ตัวเดียวกันนี้

## สิ่งที่จะสร้าง

### 1. ชนิดคำขอใหม่

| | ค่า | ป้ายไทย | Ticket ที่เปิดอัตโนมัติ |
|---|---|---|---|
| Network | `network` | คำขอใช้งานระบบเครือข่าย | ประเภท **เครือข่าย** |
| CCTV | `cctv` | คำขอใช้งานกล้องวงจรปิด | ประเภท **กล้องวงจรปิด** |

ประเภท Ticket ทั้งสองมีอยู่แล้ว (เพิ่มไปเมื่อ `88f5c8a`) — auto ticket จึงลงถูกช่องทันที

ต้องแก้ตามไปด้วย: `RequestSchemas` (ฟิลด์ของฟอร์ม) · `request-meta.ts` (ลำดับ + ไอคอน ต้องตรงกับ
เอนัม มี `RequestTypeOrderTest` คุมอยู่) · `lang/{en,th}/requests.ts` · `SlaTargetSeeder`
(หนึ่งแถวเป้าหมายต่อชนิด)

### 2. ขั้นอนุมัติแบบระบุฝ่าย

`StepActorType::Department` ใหม่ ตั้งค่าได้สองแบบ:

- **ระบุตัวบุคคล** — เลือกพนักงานคนเดียวไว้เลย ทำงานเหมือนขั้นเดิมทุกอย่าง
- **กลุ่มตำแหน่ง** — เลือกฝ่าย + ชุดตำแหน่ง ใครในกลุ่มก็อนุมัติได้ **ใครกดก่อนถือว่าคนนั้น**

โครงสร้างข้อมูล:

```
workflow_steps        + department_id        (nullable FK)
                      + approver_employee_id (nullable FK — ใช้เมื่อระบุตัวบุคคล)
workflow_step_positions  ใช้ของเดิม เป็นชุดตำแหน่งของกลุ่ม

request_approvals     + approver_department_id (nullable)
                      + approver_position_ids  (nullable JSON)
```

`request_approvals` ต้องเก็บ **สำเนา** ของเกณฑ์ ไม่ใช่อ้างไปที่ workflow เพราะคำขอที่ยื่นไปแล้ว
ต้องไม่เปลี่ยนความหมายเมื่อมีคนไปแก้ workflow ทีหลัง — หลักการเดียวกับที่ระบบเก็บ `approver_name`
ไว้แทนที่จะอ่านชื่อสดจากตารางพนักงาน

### 3. จุดที่แถวแบบกลุ่มไปกระทบ

| จุด | ตอนนี้ | ต้องเป็น |
|---|---|---|
| ประตูอนุมัติ `RequestService:702` | `me === approver_employee_id` | หรือ (แถวกลุ่ม ∧ ฝ่ายฉันตรง ∧ ตำแหน่งฉันอยู่ในชุด) |
| กระดิ่ง/อีเมลตอนถึงคิว | ส่งหาคนเดียว | ส่งหาทุกคนที่เข้าเกณฑ์ |
| เตือนคำขอค้าง | ไล่จากคนเดียว | ไล่จากทุกคนที่เข้าเกณฑ์ |
| หน้าจอ "รออนุมัติจาก" | ชื่อคน | ชื่อฝ่าย + รุ่นตำแหน่ง เช่น `ฝ่าย QC — Asst. Manager / Manager` |
| ตอนกดอนุมัติ | บันทึก `acted_by_*` | บันทึก `acted_by_*` **และ** เขียน `approver_employee_id` เป็นคนที่กด |

บรรทัดสุดท้ายสำคัญ: หลังมีคนกด แถวนั้นกลายเป็นของคนนั้นถาวร ประวัติจึงอ่านได้เหมือนแถวปกติ
และรายงานที่นับงานอนุมัติรายคนไม่ต้องรู้จักแถวแบบกลุ่มเลย

### 4. ไม่มีใครเข้าเกณฑ์

ข้ามขั้นนั้นไป พร้อมเหตุผลใหม่ `ApprovalSkipReason::NoDepartmentApprover` — บันทึกไว้ว่าข้าม
เพราะฝ่ายนั้นไม่มีคนในตำแหน่งที่กำหนด ไม่ใช่เงียบหายไป (ทำเหมือนขั้น chain ที่หาคนไม่เจอทุกวันนี้)

ตัวกันคำขออนุมัติตัวเอง (`guaranteeAnApprover`) ยังทำงานเหมือนเดิม: ถ้าทุกขั้น chain ถูกข้าม
คนสูงสุดในสายยังต้องเซ็น

### 5. หน้า Workflow

ต้องเพิ่มตัวเลือก actor type ใหม่ในหน้าแก้ workflow: เลือก "ฝ่าย" → เลือกฝ่าย → เลือกว่า
จะระบุตัวบุคคลหรือกลุ่มตำแหน่ง งานฝั่งหน้าจอส่วนนี้ประเมินแยก

## ผลกับข้อมูลจริง

- migration ทั้งหมดเป็นการ **เพิ่มคอลัมน์ที่ยอมให้ว่างได้** ไม่มีการเขียนทับข้อมูลเดิม
- คำขอที่ยื่นไปแล้วไม่ถูกแตะ — แถวเดิมมี `approver_employee_id` อยู่ ยังเดินเส้นทางเดิมทุกอย่าง
- workflow เดิม 11 ชนิดไม่เปลี่ยน — ไม่มีขั้นไหนกลายเป็นแบบฝ่ายโดยไม่ได้สั่ง
- `DefaultWorkflows` เพิ่มสองรายการ seeder ต้อง idempotent (มีอยู่แล้วก็ไม่สร้างซ้ำ)
- ตาราง SLA จะมีชนิดคำขอเพิ่มสองแถวให้ตั้งเป้าหมาย

## เทสต์ที่จะเขียน

1. คำขอ Network ยื่นแล้วได้สายอนุมัติ manager → executive → IT
2. คำขอ CCTV ยื่นแล้วได้ห้าขั้นตามลำดับที่กำหนด
3. คนในฝ่าย QC ตำแหน่งตรง กดอนุมัติแถวกลุ่มได้
4. คนในฝ่าย QC ตำแหน่งไม่ตรง โดนปฏิเสธ 403
5. คนตำแหน่งตรงแต่อยู่คนละฝ่าย โดนปฏิเสธ 403
6. สองคนในกลุ่ม คนแรกที่กดถูกบันทึกเป็นเจ้าของแถว คนที่สองกดไม่ได้อีก
7. ฝ่ายที่ไม่มีคนในตำแหน่งที่กำหนด ขั้นนั้นถูกข้ามพร้อมเหตุผล
8. แก้ workflow หลังยื่นคำขอแล้ว ไม่เปลี่ยนเกณฑ์ของคำขอที่ค้างอยู่
9. auto ticket ของ Network ลงประเภทเครือข่าย ของ CCTV ลงประเภทกล้องวงจรปิด
10. ลำดับชนิดคำขอฝั่ง PHP กับฝั่ง TS ยังตรงกัน (`RequestTypeOrderTest`)

## ทำเป็นสองระลอกได้

**ระลอกที่ 1 — Network เท่านั้น** ไม่แตะเครื่องยนต์ ใช้งานได้จริงภายในวันเดียว

**ระลอกที่ 2 — ขั้นแบบฝ่าย + CCTV** งานใหญ่กว่ามาก ทั้ง migration, resolver, ประตูอนุมัติ,
การแจ้งเตือน, ตัวเตือนคำขอค้าง และหน้า Workflow

แยกแบบนี้แล้ว Network ได้ใช้ก่อนโดยไม่ต้องรอ และถ้าระลอกที่ 2 พบปัญหาระหว่างทาง ระลอกแรก
ก็ไม่ถูกลากไปด้วย
